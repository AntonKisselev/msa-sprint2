### <a name="_qmphm5d6rvi3"></a>**Решение**
после анализа было решено выделить в отдельный микросервис - сервис "отзывов", по следующим причинам:
1. относительно просто его выделить и провести рефакторинг кода
2. он относительно независим, и другие сервисы смогут работать без него, в случае ошибок
3. в виду относительной простоты, команда сосредоточится на более организационных моментах. На общих издержках, например создания инфраструктуры, выделение доступов и тд. 
4. исходя из 3 пункта возможно получим еще дополнительные сложности, чтобы внести корректировки вначале фазы переезда

Технологии по большей своей части решено оставить прежние, в виду наличия компетенции у команды.
Так же необходимо ввести API Gateway, чтобы проксировать запросы от пользователей к системе, и выделяя необходимые запросы на микросервисы

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Альтернатива выделить сервис бронирования. Тк это по сути центральный сервис
плюсом можно считать, что в случае успеха можно будет поставить большой процент выполнения задачи перехода на микросервисы

**Недостатки, ограничения, риски**
1. процесс выделения может затянуться надолго, в виду сложности сервиса бронирования
2. скорее всего придется сильно затрагивать другие сервисы, из-за большой связности компонентов
3. риск ошибок сильно увеличивается
4. самое главное появляется риск потерять систему всю на какое-то время
Исходя из этого альтернативное решение было отвергнуто
